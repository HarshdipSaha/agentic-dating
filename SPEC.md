# Twofold — agentic dating from two public profiles

Status: implementation specification; application, completed cohort, deployments, and submission video are not built by this document.

Prepared using `/to-spec` from the supplied task, primary-source web research, and Playwright browser probes. No clarification interview was conducted. The directory was empty when work began, so there is no existing application, glossary, ADR, or test convention to preserve. Intended triage label: `ready-for-agent`. No project issue tracker was provided; this is the local issue-ready artifact.

## Problem Statement

A reviewer must be able to open a working dating website, inspect at least 25 real people's profiles derived from their official LinkedIn and public Instagram, watch their agents conduct actual multi-turn simulated dates, and see a complete individual ranking. The reviewer must also be able to paste new links and execute the same pipeline. A styled frontend, invented personas, static conversation fixtures, or a cached demo presented as a new scrape does not satisfy the task.

The submission is judged primarily through a YouTube demonstration lasting no more than three minutes. It must show profile analysis before rankings, include agents dating, and demonstrate the complete input-to-results experience. It also needs a finished demo URL, live website URL, public GitHub repository, a description of at most 200 characters, and scraping explanation of at most 500 characters.

The largest uncertainty is data acquisition and identity verification. Matching names do not establish that two accounts belong to the same person. Public profile headers do not establish Instagram public status. LinkedIn can block a logged-out browser even when a profile is indexed. The system must record these distinctions rather than silently substitute data.

## Solution

Build **Twofold**, an evidence-first agent dating lab. Each person supplies exactly one canonical LinkedIn profile and one canonical Instagram profile. The app imports those sources, builds a source-linked profile, instantiates a separate agent, and runs a round-robin of simulated first dates. Every completed date produces two independent agent reflections. Rankings derive from those completed dates and display their supporting evidence and uncertainty.

The product is a simulation. Agent dialogue is generated by software, not a quotation, endorsement, or expression of actual romantic interest by the person. Profiles summarize visible, non-sensitive interests, hobbies, and explicit goals. Relationship needs remain unknown unless expressly stated in the two allowed sources; never infer sexuality, attraction, religion, health, or private relationship intentions from photos, occupation, followers, or posting style. The score describes the simulated conversation and supported shared interests; it is not a probability that two real people will date.

This distinction must be visible in ordinary product language, while the site still performs the requested reading, dating, and ranking pipeline. If the grader expects inferred private romantic preferences or real-world participant authorization, the brief provides neither; do not claim the simulation proves those things.

The finished example is an immutable, previously executed cohort of at least 25 verified people. A separate workspace supports new imports and runs. The demo remains readable without credentials, typing, or rerunning paid services.

## Implementation Decisions

### Scope and vocabulary

- **Candidate:** discovered URL pair, not yet eligible for the demo.
- **Person:** one identity with two admitted source accounts.
- **Source snapshot:** an immutable capture of one account's allowed public content, with timestamp and provenance.
- **Evidence:** a source pointer and short supported excerpt or paraphrase owned by that person.
- **Profile:** the structured analysis of a person's two snapshots.
- **Agent:** an isolated software actor grounded in one profile, with memory scoped to a single date.
- **Date:** a multi-turn exchange between two distinct agents, with a stored event sequence and independent reflections.
- **Cohort run:** a versioned execution over a fixed set of ready profiles.
- **Ranking:** one person's ordering of the other admitted people, derived from completed dates in one cohort run.

### Stack and process boundary

- Use TypeScript throughout, Next.js with React for the website, Tailwind for presentation, Zod for provider and model output validation, PostgreSQL for durable storage, and the Apify JavaScript client for collection.
- Deploy the web app and a persistent Node worker to a host that supports long-running processes; Railway is the proposed single-provider choice. Use managed PostgreSQL. Do not depend on an in-memory queue or a short-lived request continuing after the HTTP response.
- Keep the LLM provider behind one small structured-output interface. Record the actual provider/model/version in each run. Choose the available model based on measured small-cohort latency and grounded output quality, rather than hard-coding an untested cost assumption.
- Use a database-backed job table with leases, heartbeats, attempt counts, idempotency keys, and bounded retries. For this scope, another queue service is unnecessary.
- Provide server-sent events backed by persisted events, with polling fallback. Refreshing the browser must reconstruct progress from durable records.
- Keep discovery and source collection separate. Search helps locate account URLs. Only the admitted LinkedIn and Instagram content is sent to the analysis or dating model. External bios, search snippets, podcasts, Linktree content, and official websites are not trait evidence.

### Collection adapters and the two-source boundary

- Start with `apify/instagram-profile-scraper` for Instagram. Its documented input is `usernames`; `includeAboutSection` is optional. The provider documents profile information and recent posts. Verify the returned record shape in a real trial; adapters must not assume the private flag is always named `isPrivate`. [Input schema](https://apify.com/apify/instagram-profile-scraper/input-schema), [actor documentation](https://apify.com/apify/instagram-profile-scraper).
- Start with `harvestapi/linkedin-profile-scraper` in profile-details-only mode. Its input schema includes `urls`, `queries`, and `profileScraperMode`. Pin the exact enum value from a successful trial. Disable email search, which the provider describes as independently sourced. [Input schema](https://apify.com/harvestapi/linkedin-profile-scraper/input-schema), [actor documentation](https://apify.com/harvestapi/linkedin-profile-scraper).
- The adapter must allowlist fields rather than hand the entire raw result to the model. Strip email, phone, follower graphs, related people, comments by others, external company enrichment, and third-party predictions. Do not follow bio links or collect commenters as additional people.
- Collect LinkedIn about, headline, experience, education, skills, and only permitted self-authored content available from the selected adapter. Collect Instagram biography and up to 12 recent self-authored post captions initially. Preserve per-post source URLs. Images are optional and require separate provenance; the initial scope uses text evidence and does not infer traits from faces or appearance.
- Reposts about someone else are not autobiographical evidence. Sponsored content can establish a content topic, but cannot by itself establish a personal hobby. Store these content distinctions.
- A provider's transport or cached copy of the same account is not automatically a third source. Its provenance must still identify the two requested accounts. Reject enrichment from independent sources and any result whose account identity or origin cannot be established.
- Persist actor ID, input fingerprint, build/run ID, dataset ID, capture time, requested and resolved account identity, private status, result status, and source content fingerprint. Use server-side authentication. [Apify client workflow](https://docs.apify.com/api/client/js/docs/introduction/quick-start).
- Start collection asynchronously, retain run IDs, and poll from the worker. Webhooks are optional; if used, authenticate the callback and confirm the referenced run server-side. Success of the Actor is insufficient: also validate that the expected person's row contains usable content. [Run API](https://docs.apify.com/api/v2/actors-runs-post), [webhook events](https://docs.apify.com/integrations/webhooks/events).
- An Instagram private flag must be explicitly false and mapped from the tested output schema. Unknown/missing status is not public. Profile headers or HTTP 200 alone cannot pass this gate.
- Require both usable source snapshots before analysis. Never substitute a model's background knowledge when a source is blocked. If credentials are absent, return a setup error and keep the profile pending.

### Identity admission

- Normalize only HTTPS URLs from approved LinkedIn and Instagram hosts. Accept LinkedIn personal `/in/` profiles and Instagram profile handles, not company pages, posts, reels, exploration pages, or arbitrary redirect URLs. Disallow embedded credentials, off-host redirects, loopback addresses, and generic URL fetching.
- Store platform account IDs when available to detect duplicate people across changed usernames.
- Prefer a direct cross-link between the two accounts. Otherwise require a documented manual review of matching name plus multiple distinguishing, non-sensitive profile facts, such as the same creator alias and named project. A shared name or similar profile image is insufficient. Do not use facial recognition.
- Automatically mark uncertain pairs `IDENTITY_REVIEW_REQUIRED`; do not invent a match. New visitor workspaces may run verified imports without an operator interview. Unresolved imports remain visible but excluded from dates.
- The research candidate list is an acquisition starting point. It is not the finished cohort. Do not count it toward the 25 until all admission checks pass. Maintain reserves because some candidates will be blocked, private, or ambiguous.

### Profile analysis

- Analysis returns identity summary, supported interests, supported hobbies, explicit goals/needs, observed public activities, optional non-sensitive tentative interpretations, evidence IDs, confidence labels, and unknowns.
- Confidence labels concern evidence support, not psychological certainty. Do not assign personality diagnoses or infer private romantic desires. A public interest in travel does not imply a desire for an adventurous partner.
- Every displayed claim must cite at least one evidence record whose ownership matches the person and whose origin is one of their two snapshots. Reject invalid evidence IDs; allow one constrained repair attempt, then fail analysis explicitly.
- Need and hobby sections are allowed to be empty with a clear explanation. A robust profile with honest unknowns is better than a full card of invented traits.
- Use retrieved excerpts as untrusted data, not instructions. The analyzer has no browsing tools. It cannot fetch sources beyond the two snapshots or import facts remembered by the model.
- Store source versions and analysis prompt/schema versions. A refresh creates a new profile version and invalidates future use of old rankings as current results; historical runs remain labeled and inspectable.

### The dating harness

- Run every unordered pair once: for exactly 25 people, there are 300 pairwise dates. Each person therefore appears in 24 dates. A pair returns two directional reflections, yielding 600 ranked directional outcomes.
- Give each agent its own person's profile/evidence and a separate system instruction. Do not have one model call write both sides of an entire conversation. The opponent's visible statements and public introductory card are interaction inputs, derived solely from that opponent's allowed sources; they are not new external biographical sources.
- A neutral host selects a fictional first-date activity from supported shared topics. The host may propose a cafe or gallery scenario without claiming a real reservation, attendance, preference, or physical outing.
- Use four phases with one turn from each agent in each phase: introduction; activity exploration; a concrete trade-off; next-step reflection. This produces eight sequential turns per pair. Vary who starts deterministically by pair ID to reduce systematic opener bias.
- Each agent reads the prior transcript before its next turn. It must acknowledge the previous partner turn, make a grounded contribution, and either ask a specific question or answer one. Merely alternating independent profile summaries does not pass.
- Example trade-off: two agents discuss a creative workshop versus a quiet reading session based on evidenced interests. They negotiate a plan or state what is unknown; the host never fabricates real people's schedules or relationship boundaries.
- Label speech as “Agent for [name]”. Maintain software-generated simulation labeling during live dates and replay. An agent may speak naturally within the simulation, but cannot present unsupported private claims as its person's beliefs.
- Record observable decisions and evidence references. Do not expose hidden chain-of-thought. Provide concise grounded explanations that a reviewer can inspect.
- After eight turns, each agent independently reflects using its own supported interests, the visible exchange, and the partner's grounded contributions. Reflections record strengths, frictions, unanswered questions, evidence IDs, and rubric dimensions. Reflections do not authorize contacting either person.
- Validate each turn's evidence ownership. A person-specific self-claim must point to that person's evidence. Facts relayed by the other agent remain attributed rather than promoted to verified source facts.
- Run bounded concurrent pairs, starting with six and tuning from measured provider limits. Turns within a pair remain sequential. Save each turn before broadcasting its event.
- Persist token usage, latency, model, run version, and attempts. Set a maximum conversation length and per-run cost ceiling. A pair over its limit ends as failed, with an actionable retry.

### Ranking decisions

- Each directional reflection returns four ordinal rubric scores, 0–5: supported shared-interest exploration; reciprocal conversational engagement; constructive handling of the concrete choice; and a grounded possible follow-up activity.
- Convert the fixed rubric to a simulation score: `100 × (0.35 × interests + 0.25 × engagement + 0.25 × negotiation + 0.15 × follow-up) / 5`. These weights are a product decision, not research-validated romantic predictors. Display the dimensions and uncertainty alongside the total.
- Use unknown for dimensions that cannot be assessed. Withhold the aggregate when a required dimension is unknown; do not impute a high score from missing evidence. Explain the omitted pair in the ranking page.
- Directional fit A→B can differ from B→A because reflections evaluate different grounded interests. Show reciprocal balance as the minimum of the two complete scores, with both directional scores accessible.
- Sort by descending directional score; use stable person ID for deterministic ties. A completed ranked list excludes self, contains no duplicates, and links every score to its date and reflection.
- Interim results clearly state completed coverage. A full demo is complete only when all 300 dates and 600 assessments exist, with 25 lists of 24 assessed partners. A failed or unassessable pair blocks the complete-demo gate.
- Never generate a score directly from names, photos, follower counts, presumed gender, sexuality, popularity, or model knowledge of a public figure. Keep romantic compatibility and sensitive preference inference outside the rubric.

### Product screens

1. **Cohort home:** two URL inputs, import action, searchable person grid, real source/analysis status, and entry to the finished example.
2. **Person profile:** official source links, identity check, source freshness, needs/hobbies/interests, evidence drawer, coverage and unknowns, and agent readiness.
3. **Date room:** selected pair, supported activity, eight-turn phase timeline, streaming agent messages, evidence actions, run status, and independent reflections. Stored replay has a visible replay label.
4. **Run overview:** completed pairs out of the actual total, per-person coverage, live date selection, failures and retries, and readiness for ranking.
5. **Rankings:** person selector, 24 partner entries for a complete 25-person cohort, directional score, reciprocal score, rubric, grounded explanation, unanswered questions, and transcript links.
6. **Submission demo:** immutable cohort, profile-first entry, date-room access, completed rankings, source manifest, and run metadata.

Use a warm editorial visual style: ivory canvas, dark ink, terracotta accents, generous type, restrained motion, and readable evidence cards. Keep the profile, agent conversation, and ranking visually distinct. Avoid decorative progress counters, fake notifications, and unsupported score claims. Provide accessible contrast, focus visibility, reduced motion, and mobile single-column views.

### Data contracts

- A Person owns exactly two SourceAccount records, constrained to one of each platform.
- A SourceSnapshot owns provider provenance and allowed content items. Raw provider payloads stay private; the public evidence export contains only the admitted subset.
- Evidence belongs to a person and a snapshot, with a profile-field or authored-post locator, a short excerpt/paraphrase, content timestamp when available, and capture time.
- ProfileVersion references its exact two snapshots and versioned analyzer. An AgentVersion references one ProfileVersion.
- CohortRun freezes ordered person and agent versions. PairDate is unique by cohort run and unordered agent pair.
- DateTurn is unique by pair and turn ordinal, with agent ID, role, visible content, evidence references, and model request metadata.
- Reflection is unique by pair and reflecting agent. RankingSnapshot references the cohort run and completed directional reflections.
- Job and Event records provide durable execution and reconnectable progress; only workers and authenticated operators can mutate the immutable submission example.
- Public JSON exports expose source URLs, evidence, visible transcripts, rubric results, and reproducibility metadata. They omit API tokens, internal reasoning, contact data, and arbitrary raw provider fields.

### API contracts

- Create a workspace with an unguessable identifier and mutation token; public demo IDs support read-only access.
- Create an import from two URLs with an idempotency key; return an import ID and accepted status immediately.
- Get import status with separate source and identity/analysis stages; include recoverable error codes and next action.
- Get a profile version and its evidence after analysis. Failed imports do not return placeholder-success profiles.
- Add ready profiles to a workspace and create a frozen cohort run with at least two distinct people.
- Get run status and persisted progress events using a cursor. Support event reconnect without replaying duplicate writes.
- Get a date's stored turns, phase, reflections, and current execution state. Retry only the failed work under the same unique pair.
- Get one person's rankings for a chosen run version, including coverage and unassessed partners.
- Export a completed demo manifest and visible run artifacts. Reject public mutation of the submitted example.
- Refresh, delete, and retry operations are scoped to the owning workspace. Deleting a person must remove associated workspace artifacts or explicitly invalidate their referencing runs; never leave a misleading current score behind.

### Failure and execution states

- Import: `QUEUED → FETCHING → VALIDATING → ANALYZING → READY`.
- At validation, branch to `PRIVATE_SOURCE`, `SOURCE_UNAVAILABLE`, `IDENTITY_REVIEW_REQUIRED`, `IDENTITY_MISMATCH`, or `INSUFFICIENT_EVIDENCE`.
- At any external operation, branch to a typed retryable or terminal failure. Show provider/configuration failure accurately without exposing secrets.
- Run: `QUEUED → RUNNING → ASSESSING → COMPLETE`, with explicit partial and failed states.
- Date: `PENDING → LIVE → REFLECTING → COMPLETE`; resumed workers continue from the last committed turn. Retried model calls can vary, but only one committed turn per ordinal is visible.
- Lease a job transactionally and heartbeat it. On lease expiry, another worker resumes from committed state. A stale worker cannot overwrite a newer lease owner's writes.
- Provider success with missing output is failure. An interrupted stream is a transport event, not evidence that the worker failed.

## Testing Decisions

There is no prior application or test suite. The primary seam is the public workflow API backed by real storage, with external collection and generation providers replaced at their boundaries for deterministic integration tests. Browser checks exercise that same API through the UI. Live provider probes remain separate evidence of acquisition feasibility; mocked success cannot establish that a scraper works.

The user instructed that no questions will be answered. Therefore, the `/to-spec` seam-confirmation step is resolved here by best judgment, without pausing for approval.

- Test externally visible behavior: submitted links lead to a profile, real generated turns, linked reflections, and rankings; failures remain honest. Do not test private helper arrangements or mirror implementation code.
- Test a complete three-person cohort: three dates, six directional assessments, three lists of two unique partners, self exclusion, valid transcript links, deterministic ties, and source ownership. Use it as the fastest complete vertical slice.
- Test the 25-person cardinalities independently against a seeded integration run: 300 unique pairs, 24 dates per person, 600 directional results, and 25 full lists of 24. Include a deliberately missing pair to prove the completion gate fails.
- Test private true, private false, missing private flag, differently named mapped private flag, empty dataset, malformed JSON, missing profile fields, non-matching returned username, source timeout, and HTTP/provider errors.
- Test same-name different-person input, cross-linked identity, insufficient identity evidence, duplicate canonical URLs, changed usernames with equal platform IDs, and LinkedIn company URL rejection.
- Test source discipline using a payload with company enrichment, email, related accounts, external links, and hostile caption instructions. Assert that none enter analysis prompts, evidence, transcript self-claims, or scores.
- Test that invalid evidence references, sensitive inference, unsupported needs, and fabricated preference claims are rejected or omitted, while a legitimate empty needs section is displayed correctly.
- Test agent interaction through the provider request contract: agent B receives committed A's turn; A's next turn receives B's response; each speaker receives its own scoped profile. Do not use a scripted fixture as proof of live agent behavior.
- Test worker crash and expired lease between turns, duplicate event delivery, browser reconnection, retry after reflection failure, and competing workers. Assert exactly one visible turn and reflection for each unique position.
- Test incomplete versus complete rankings, asymmetric assessments, unknown dimension withholding, stable tie order, and evidence coverage separated from total score.
- Test workspace isolation, immutable demo mutation rejection, secret redaction, arbitrary-host URL rejection, and bounded run execution.
- Use Playwright for desktop/mobile input-to-ranking flow, keyboard navigation, accessible form errors, profile-before-ranking navigation, transcript expansion, evidence links, reload persistence, and replay labeling.
- Run a live two-person scrape/analysis/date probe with valid credentials before scaling. Save actual provider IDs and output-shape checks. Then execute the admitted 25-person cohort and audit every manifest row, not only a screenshot.
- Inspect the final video duration programmatically and open every submitted URL in a fresh browser context. Playwright records browser video when configured; close the context before consuming the video artifact. [Playwright video guidance](https://playwright.dev/docs/videos).

## Out of Scope

- Inferring or predicting sensitive personal traits, sexuality, actual romantic attraction, hidden relationship status, health, or psychological diagnoses.
- Contacting the real people, sending messages, arranging physical dates, or claiming that the public-profile people authorized the generated dialogue.
- Private profiles, login-wall circumvention through borrowed accounts, credentials requested from participants, or collecting private content.
- Third-party biography enrichment, external websites as trait evidence, email discovery, follower graphs, and related-account mining inside a person's analysis.
- Authentication-heavy social networking features, real chat, payments, invitations, calendar booking, mobile native apps, elaborate recommendation learning, or proprietary browser infrastructure.
- Generated fictional people counted toward the 25-real-person requirement.
- Fake scrape progress, scripted dialogue presented as live model output, and precomputed ranks presented as a newly executed run.
- Guaranteeing that arbitrary social links will be retrievable regardless of privacy status, platform restrictions, or provider outage. Supported requests must run; unsupported requests must fail explicitly.

- At least 25 distinct admitted real people, each with two official identity-matched accounts and explicit public Instagram status at capture time.
- Source-linked profiles with truthful coverage, including unknown needs where appropriate.
- One completed frozen run with all 300 actual multi-turn dates, independent reflections, and 25 full rankings.

- A public live URL accepting new valid source pairs and executing the same real pipeline, with honest failure handling.

- A YouTube video of at most 180 seconds, showing analysis/profile pages first, real agent turns, and then rankings, plus the input-to-result workflow.
